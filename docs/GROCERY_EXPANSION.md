# Grocery expansion and checkout fixes

## Behavior
- Stock preflight remains workspace-scoped and transactional but no longer takes a product write lock. Checkout still locks and verifies stock before allocating it.
- Workspace membership is resolved once per actor within a single availability request or import checkpoint, never cached across requests/checkpoints. The client timeout is 30 seconds.
- New PO and carryover numbers use Asia/Manila `PO-YYYYMMDD-000001`, retaining the global locked sequence. Old IDs remain unchanged; mixed-format carryovers compare sequence numbers.
- Supplier creation, editing, notes and product links persist through scoped APIs. Purchase item selection includes explicitly linked supplier products.
- Display labels use Status, Rejected, Near Expiry, Search Products, Amount Tendered, and Complete Sale. Stored workflow values remain compatible. Broken UTF-8 labels were repaired.

## Migration and import
Run migrations first. Two migrations add grocery expansion checkpoints and nullable supplier notes; existing rows are preserved.
The existing `LOAD_GROCERY_PRESENTATION=true` startup job runs the original loader with `--expand` after the server starts. Existing configured Admin/Manager emails are reused. Expansion requires the verified completed original grocery import, and refuses mismatched ownership.

Manual preview:
`php artisan presentation:expand-grocery ADMIN_EMAIL MANAGER_EMAIL`
Apply/resume: same command with `--apply`.

Expansion adds 70 products, 5 suppliers, 5 categories, 30 subcategories, 49 purchase requests, 154 receiving batches, 350 cash sales, and 8 stock adjustments. Together with the original import the targets are 120 products, 15 suppliers, 15 categories, 40 subcategories, 304 batches, 500 sales and 200 distinct PO/request records. Pending/rejected requests intentionally do not create approved purchase orders.

Examples include pending, reviewed pending, rejected, approved awaiting delivery, cancelled, full receiving, partial receiving, damaged returns and a posted replacement. Four products have 20 near-expiry batches (1–5 days after the first import date); two have 10 expired batches. Approved damage adjustments produce zero/low stock examples; rejected and pending adjustments leave stock unchanged. Sales use historical dates up to the first import date; reruns do not continually add new daily sales or move expiry dates.

Checkpoint records and domain changes commit together. Interrupted checkpoints roll back and resume; previously completed steps are skipped. This is presentation data, not recovered historical business data. No customer emails or external payments are sent. Internal workflow audit entries/notifications are generated by the normal domain services.

## Verification
Targeted tests cover stock exclusion and checkout, ownership, supplier persistence, PO numbering/carryovers, expansion interruption/resume, no duplicates, batch/stock reconciliation, near-expiry and expired quantities, replacement posting, and cross-account denial. UI tests and production asset build are also required.
Production timeout resolution and import counts must be verified after deployment; local tests do not establish production latency. Render Live means the web server is ready, not that the background expansion has finished. Look for `Grocery expansion complete. Checkpoints committed; rerunning does not duplicate records.`
